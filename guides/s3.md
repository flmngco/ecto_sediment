# S3-backed repos

With the `:s3` option, a repo's database lives in an S3 bucket. The local
file is a working copy: commits are uploaded to S3 in the background (or
before they return, with `sync: true` or `durability: :sync`, see
"Durability"), and a repo that starts on a machine without the local file (or
with a stale one) restores the database from S3 first.

> #### The S3 copy wins over the local file {: .warning}
>
> * When the prefix holds a database, starting the repo **replaces** the local
>   files at `:database` (the file, its `-wal` and `.db-log`) with the S3
>   state. Local changes that never reached S3 are discarded.
> * Adding `:s3` to a repo whose database file already has tables doesn't
>   upload it. On an empty prefix the repo can't connect: the logs show
>   `"s3 config: ... refusing to replace the local file ..."`, and the file is
>   left alone. To move existing data to S3, import it (see "Importing an
>   existing database").

This guide covers using that from Ecto: configuration, deployment and
operations. The storage design, the exact guarantees and the S3 request costs
are described in sediment's S3 guide and `Sediment.S3`.

## Configuration

In a Phoenix application, keep development and tests on a plain local
database and configure S3 in `config/runtime.exs` for production:

```elixir
# config/runtime.exs
if config_env() == :prod do
  config :my_app, MyApp.Repo,
    database: System.get_env("DATABASE_PATH", "/data/my_app.db"),
    pool_size: String.to_integer(System.get_env("POOL_SIZE", "5")),
    # reconnect quickly when taking over the writer lease (see "Deploying")
    backoff_min: 100,
    backoff_max: 1_000,
    # S3 databases are encrypted: 64 hex characters, e.g. `openssl rand -hex 32`
    encryption: [cipher: "aegis256", key: System.fetch_env!("DATABASE_ENCRYPTION_KEY")],
    s3: [
      bucket: System.fetch_env!("S3_BUCKET"),
      prefix: System.get_env("S3_PREFIX", "prod/my_app"),
      region: System.get_env("AWS_REGION", "us-east-1"),
      # the standard AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY variables are
      # used when these are omitted
      access_key_id: System.get_env("AWS_ACCESS_KEY_ID"),
      secret_access_key: System.get_env("AWS_SECRET_ACCESS_KEY"),
      # for S3-compatible servers (SeaweedFS, MinIO, R2, ...)
      endpoint: System.get_env("S3_ENDPOINT"),
      # the machine's hostname: $HOSTNAME is often unset in releases
      owner: System.get_env("S3_OWNER") || (:inet.gethostname() |> elem(1) |> List.to_string()),
      # keep the last 24 epochs (one per checkpoint) for point-in-time restore
      retain_epochs: 24
    ]
end
```

* The bucket must exist. The prefix holds one database; use one prefix per
  repo.
* The provider must enforce conditional PUTs (`If-None-Match: *`, `If-Match`);
  sediment probes this on the first open and refuses providers that
  don't. AWS S3, MinIO, SeaweedFS and Tigris work (ecto_sediment's S3 test
  suites and the ecto/ecto_sql integration suites in S3 mode run against
  SeaweedFS and passed against MinIO when tested; sediment tests Tigris,
  including a 12-hour multi-node soak); Cloudflare R2 should. Google Cloud Storage's S3 API does
  not. See sediment's `guides/s3_providers.md`.
* The directory of `:database` must be writable. It only holds the working
  copy, so it doesn't need to be a persistent volume: an empty disk restores
  from S3 on start. A persistent volume doesn't save the restore, since each
  start downloads the latest snapshot and log again.
* `journal_mode` defaults to `:mvcc` for S3 repos (S3 requires it), so
  `BEGIN CONCURRENT` is available. In MVCC mode use integer primary keys
  (Ecto's default `AUTOINCREMENT` keys are much slower there and conflict
  under concurrent writes), in `config/config.exs` so every environment
  creates the same schema:

  ```elixir
  config :my_app, MyApp.Repo, migration_primary_key: [type: :integer]
  ```
* `:owner` identifies the writer. Give each node a stable owner of its own:
  a node that restarts with the same owner takes its lease back immediately,
  while a different owner waits until the old lease is released or expires
  (`lease_ttl_ms`, 30 s by default). Never give two nodes that run at the
  same time the same owner: each would take over the other's lease. In
  containers the hostname usually changes with every container, which is safe
  (a cleanly stopped container releases its lease) but means a replacement
  for a crashed container waits for the lease to expire; set `S3_OWNER` to a
  stable per-node value (a volume id, a machine id) to avoid that wait.
* **S3 databases are encrypted by default.** A repo with `:s3` needs
  `:encryption` with a key, or `encryption: false` to store the database
  unencrypted; with neither it refuses to connect. The data in the bucket is
  encrypted at rest (snapshots and log frames), and every restore (a node
  starting, a replica, `mix ecto.sediment.s3.restore`) needs the same key:
  keep it somewhere safe, since without it the data in S3 can't be read.
  `Sediment.S3.generate_key/0` or `openssl rand -hex 32` generates one. An
  unencrypted database stays unencrypted: open it with `encryption: false`.
  In-memory databases can't be S3-backed.

## Durability: async by default, sync when it matters

With the default `durability: :async`, a commit returns as soon as it is in
the local log. A background uploader sends committed transactions to S3 in
commit order, usually within milliseconds. If the machine dies before the
uploader caught up, the last acknowledged commits are lost. `:max_lag_ms`
(1 s by default) is a backpressure threshold, not a bound on that loss: once
the oldest un-uploaded commit is that old, new commits wait for the uploader,
so an S3 outage doesn't turn into unbounded loss. A crash loses the commits
not yet uploaded, including the upload in flight and, with
`:upload_interval_ms`, up to that interval of commits collected for the next
upload. What a restore returns is always the database
as of some moment: a prefix of the commits in order, never a later commit
without an earlier one, and never half a transaction. This is the trade-off
Litestream makes.

When a write must not be lost once it is acknowledged, ask for it:

```elixir
# waits until this commit is durable in S3 (any Repo function takes :sync)
Repo.insert!(order, sync: true)
Repo.transaction(fn -> ... end, sync: true)

# waits until everything committed so far is durable
:ok = Ecto.Adapters.Sediment.s3_flush(MyApp.Repo)
```

or make every commit wait, for the whole repo:

```elixir
config :my_app, MyApp.Repo, s3: [durability: :sync, ...]
```

or per repo module, for writes only, with Ecto's `default_options/1` (opt
out with `sync: false`):

```elixir
defmodule MyApp.Repo do
  use Ecto.Repo, otp_app: :my_app, adapter: Ecto.Adapters.Sediment

  @writes [:insert, :update, :delete, :insert_or_update, :insert_all, :update_all,
           :delete_all, :transaction]

  def default_options(operation) when operation in @writes, do: [sync: true]
  def default_options(_operation), do: []
end
```

Keep `sync: true` off reads (`:all`, which `get` and `one` use too,
`:stream`, `:preload`, `:reload`): a read has nothing of its own to make
durable, and it would wait for the writes of every other connection instead.

Details:

* **Visibility precedes durability.** Other connections see a commit as soon
  as it is committed locally, before it is in S3. A request can read data
  that a crash a moment later would lose. Use `sync: true` for writes whose
  effects leave the system (an email sent, a payment confirmed) before you act
  on them.
* **`sync: true` inside a transaction** applies to the transaction: pass it to
  `Repo.transaction/2`; on a statement inside a transaction (or an
  `Ecto.Multi`) it has no effect, since nothing is committed when it returns.
  A sync commit waits for everything committed before it too (commits become
  durable in order). It waits at most `:sync_timeout` (default: the query's
  `:timeout`); if S3 can't be reached in time, the call fails with
  `"committed locally, but not known to be durable in S3: ..."`. The commit is
  *not* rolled back: it is visible locally and becomes durable once S3 is
  reachable, unless the machine dies first.
* **Backpressure.** If S3 is slow or down, the upload queue is bounded by
  `:max_lag_ms` and `:max_pending_bytes` (16 MiB by default): beyond that, new
  commits wait for the uploader, so an outage can't silently grow the amount
  of data at risk. If the uploader keeps failing, or finds that another
  writer took over, it stops the writer: commits fail with
  `"s3 writer fenced: ..."`, the connections reconnect and restore the durable
  state from S3, and the commits that weren't uploaded yet are gone.
* **Checkpoints** wait for the queue first. **Stopping the repo** (with the
  application, or `Supervisor.stop/1`) uploads what is pending too, for up to
  `:close_timeout_ms` (10 s by default; the repo's supervisor waits that
  long): with S3 unreachable for longer, the rest is lost and logged. Call
  `s3_flush/2` before stopping when you need to know. A crash, `kill -9`, or
  losing the machine loses what wasn't uploaded yet.
* **Scripts and Mix tasks** (`mix run priv/repo/seeds.exs`, custom tasks,
  `elixir` scripts) end with `System.halt/1`, which doesn't stop the repo;
  sediment registers a `System.at_exit/1` hook that uploads what every
  open S3 database still has queued first (warning about anything it couldn't
  make durable), so a script's commits aren't lost. Code that calls `System.halt/1` itself bypasses the
  hook: call `s3_flush/2` before.
* **Lost commits are reported.** When commits that were acknowledged
  are lost (the writer was fenced, or stopped while S3 was unreachable, with
  commits still queued), the repo reconnects and restores what is durable,
  and from then on `s3_flush/2` and `sync: true` fail with
  `"s3 commits were lost: ..."` (the `lost` field of `s3_info/1` says which
  range). Once the application has dealt with it (re-applied or reported the
  lost writes), `Ecto.Adapters.Sediment.s3_acknowledge_loss(MyApp.Repo)` clears
  it.
* `Ecto.Adapters.Sediment.s3_info/1` shows how far the uploader is behind (see
  "Observability").
* With `durability: :sync` every commit waits for S3 (see "Performance"). `sync: true` and `s3_flush/2` are no-ops
  then, so code using them works in both modes.

## Creating the database and migrating

`mix ecto.create` (`storage_up/1`) opens the database once: an empty prefix
creates a new database in S3, and an existing one is restored. An empty
prefix never replaces a local database file with tables (see the warning
above, and "Importing an existing database" to upload one). Migrations then
run as usual and are stored in S3 like any other write.

**Migrations can only run on the node that holds the writer lease.** A
migration started elsewhere can't connect and fails after the pool's queue
timeout with a `DBConnection.ConnectionError` (the logs show `"s3 lease held
by <owner>"`).

With a release, the usual `MyApp.Release.migrate/0` works when nothing else
is writing, e.g. on a single node between stopping the old version and
starting the new one (`bin/my_app eval "MyApp.Release.migrate()"`):

```elixir
defmodule MyApp.Release do
  @app :my_app

  def migrate do
    Application.load(@app)

    for repo <- Application.fetch_env!(@app, :ecto_repos) do
      {:ok, _, _} = Ecto.Migrator.with_repo(repo, &Ecto.Migrator.run(&1, :up, all: true))
    end
  end
end
```

`with_repo/2` stops the repo afterwards, which releases the lease. For
deploys where the new version starts while the old one is still running, run
migrations after the new node took over, see below.

`storage_status/1` and `storage_down/1` (`mix ecto.drop`) only look at the
local working copy. Dropping does **not** delete the data in S3 (it logs a
warning saying so); delete the prefix with S3 tools to start over.

## Importing an existing database

An app that ran on a plain database (ecto_sqlite3 or ecto_sediment without
`:s3`) moves its data to S3 with an import, once:

```console
# with the application stopped, and :s3 in the repo's configuration
$ mix ecto.sediment.s3.import -r MyApp.Repo
Imported the database into MyApp.Repo's S3 prefix: %{rows: 48210, objects: 12, ...}
```

or from a release, with a function next to `MyApp.Release.migrate/0`
(`bin/my_app eval "MyApp.Release.import_to_s3()"`):

```elixir
def import_to_s3 do
  Application.load(:my_app)
  {:ok, _} = Application.ensure_all_started(:sediment)
  {:ok, info} = Ecto.Adapters.Sediment.s3_import(MyApp.Repo)
  IO.inspect(info, label: "imported")
end
```

The repo's `:database` file (or `--source PATH`) is read from a copy and never
written to. Its schema and rows are copied into a new MVCC database (ids and
AUTOINCREMENT sequences, indexes, views, triggers and foreign keys included),
checked, and uploaded as the prefix's first state; then start the application
with `:s3` as usual. It restores the imported database over the file.

* The prefix must be empty. A failed import (or one interrupted by a crash)
  leaves nothing a repo would use, so run it again.
* The new database is encrypted with the repo's `:encryption` key (an
  encrypted source file is read with it too), or stored unencrypted with
  `encryption: false`; the repo needs one of the two (see "Configuration").
* `--verify restore` also downloads the imported database and compares it
  (the default checks checksums).
* WITHOUT ROWID tables and virtual tables (fts5) aren't supported with MVCC:
  the import refuses them. Turso's FTS indexes replace fts5.
* Ids continue where they were, also when the newest rows were deleted or a
  table was emptied. Only an emptied table whose CHECK constraints refuse a
  placeholder row (zero, empty text) restarts its ids at 1; the task prints a
  warning for it.
* Speed: about 5,000 to 7,000 rows/s into AUTOINCREMENT tables (every Ecto
  table, whatever the row size; a turso_core 0.8.1 cost per insert, which
  the application pays after the import too), about 25 MB/s for others,
  plus the upload. Plan roughly 4 minutes of downtime per million rows, and
  time a run on a copy into a scratch prefix first.
* Changes made to the file during or after the import aren't in S3: stop
  every writer first.

The import copies rather than switching the file to MVCC because in
turso_core 0.8.1 that switch breaks AUTOINCREMENT tables (Ecto's ids).

## Back to SQLite

`mix ecto.sediment.export_sqlite -r MyApp.Repo -o app-sqlite.db` writes the
repo's database, read from S3 (the application may keep running), to a plain
SQLite file that ecto_sqlite3 opens: same schema, rows and AUTOINCREMENT
sequences, checked before it is written. A database with Turso FTS indexes
needs `--drop-fts`. See sediment's "Leaving Sediment" guide for what the
export does and its limitations.

## One writer, many readers

Only one repo instance can write to a prefix at a time. A second writer
can't connect: its connections fail with `"s3 lease held by <owner> until
<unix ms>"` and the pool keeps retrying in the background, so it takes over
automatically once the first writer stops.

To read on other nodes, configure a read-only replica repo on the same
prefix with its own local path:

```elixir
defmodule MyApp.ReplicaRepo do
  use Ecto.Repo, otp_app: :my_app, adapter: Ecto.Adapters.Sediment, read_only: true
end

config :my_app, MyApp.ReplicaRepo,
  database: "/var/lib/my_app/replica.db",
  # the writer's key (or `false` for an unencrypted database)
  encryption: [cipher: "aegis256", key: System.fetch_env!("DATABASE_ENCRYPTION_KEY")],
  s3: [bucket: "...", prefix: "prod/my_app", mode: :replica]
```

A replica is restored when it starts and doesn't follow the writer by itself:
call `Ecto.Adapters.Sediment.s3_refresh(MyApp.ReplicaRepo)` (for example from a
periodic job) to catch up. The connections of a replica pool share one working
copy: `s3_refresh/1` downloads the new state once, and each connection switches
to it at its next query, so for a moment queries on different connections can
see the old and the new state. Replicas never write
to S3 and don't need the lease, so any number can run. Writes on a replica
fail with `attempt to write a readonly database`; send them to the writer repo.
A replica sees what is durable in S3: with async durability a commit reaches
it once uploaded, so for read-your-writes through a replica, write with
`sync: true` (or call `s3_flush/2` on the writer) before `s3_refresh/1`.

For one database per tenant (one repo module, a dynamic repo per tenant, an
S3 prefix each), see [Multi-tenant apps](multi_tenant.md): it covers starting
and stopping tenant repos, routing tenants to nodes under the single-writer
lease, and what each open tenant costs.

## Deploying

S3 repos have exactly one writer. What that means for the common deploy
strategies:

**Restart in place (one node).** Stop the old release, optionally run
migrations, start the new one. A clean shutdown releases the lease and the
restarted node uses the same owner anyway, so the new release connects at
once. Writes are unavailable for the restart plus the restore (downloading
the latest snapshot and the log since it). A node that starts while S3 is
unreachable still boots: its repo keeps retrying (queries fail with
`DBConnection.ConnectionError` meanwhile) and connects once S3 is back.

**A second node starts while the first is running** (rolling or blue-green
deploys, or an accidental second instance). Its repo can't connect: every
connection attempt fails with `"s3 lease held by <owner>"` and is retried
with the pool's backoff, and queries on that node fail with
`DBConnection.ConnectionError`. Nothing is written and the running node is
not affected. As soon as the first node stops (or its lease expires after a
crash), the waiting node connects, restores the latest state and becomes the
writer, without a restart.

**Deploys with minimal write downtime.** A single writer can't hand over
without a short gap, but it can be made small:

1. Keep migrations backward compatible (expand, then contract in a later
   deploy), as for any rolling deploy: the new version starts before its
   migrations have run.
2. Give the new node a readiness check that only passes once its repo is
   connected, so the load balancer keeps sending traffic to the old node
   while the new one waits for the lease:

   ```elixir
   # in a Plug or Phoenix controller used as the readiness probe
   def ready?, do: match?({:ok, _}, MyApp.Repo.query("SELECT 1", [], timeout: 1_000))
   ```

3. Start the new node. Its repo waits for the lease (step "A second node
   starts" above).
4. Stop the old node gracefully. Optionally checkpoint first
   (`Ecto.Adapters.Sediment.checkpoint(MyApp.Repo)` in a pre-stop hook), which
   shortens the new node's restore to a snapshot download. Its shutdown
   releases the lease.
5. The new node connects within `backoff_max` (1 s in the config above) plus
   the restore time, its readiness check passes and it receives traffic.
   Now run pending migrations on it. Requests keep running meanwhile, and a
   transaction that overlaps a migration's DDL can fail with
   `"Database schema changed"` (retry it, see the README's retry recipe), so
   keep migrations short. For example, from a task started after the repo
   that waits for a connection:

   ```elixir
   # in MyApp.Application's children, after MyApp.Repo
   {Task, fn -> MyApp.Release.migrate_when_connected() end}

   # in MyApp.Release
   def migrate_when_connected do
     case MyApp.Repo.query("SELECT 1") do
       {:ok, _} -> Ecto.Migrator.run(MyApp.Repo, :up, all: true)
       {:error, _} -> Process.sleep(500) && migrate_when_connected()
     end
   end
   ```

Writes that reach the old node during its shutdown are either committed (and
restored by the new node) or fail. Call `s3_flush/2` on the old node before
stopping it, so no acknowledged commit is left in its upload queue.

**Moving to another machine or region** works the same way: the new node
needs only the configuration, not the old disk.

**Crash recovery.** Start the repo anywhere; it restores every durable
commit (with `durability: :async`, the last acknowledged commits before the
crash may be missing, see "Durability"). After a crash the lease must expire
first (`lease_ttl_ms`) unless the restarted node uses the same owner.

**Clocks.** Safety never depends on clocks: S3's conditional writes fence a
stale writer whatever the clocks say. Availability during a takeover (a
deploy starting the new node while the old one stops) does: the writer lease
assumes node clocks agree to within `lease_ttl_ms`. With a larger skew, two
nodes can each judge the other's lease expired and keep taking over, each
fencing the other, so neither serves until the skew is fixed (nothing is
lost). Keep node clocks synchronized with NTP, or with HTTPS time sync (for
example `htpdate`) where UDP port 123 is blocked.

## Errors your application can see

| Error | Meaning | What to do |
| ----- | ------- | ---------- |
| `Sediment.Error` `"committed locally, but not known to be durable in S3: ..."` from a write with `sync: true` | The commit happened locally, but S3 didn't confirm it within `:sync_timeout`. | Treat it as not durable yet: retry `s3_flush/2` later, or check the data after an outage. |
| `Sediment.Error` from a write with `durability: :sync`, e.g. `"s3 store: ..."`, timeouts | The commit could not be stored in S3 and was rolled back. | Retry the transaction when S3 is reachable again. |
| `"s3 lease held by ..."` in the logs, `DBConnection.ConnectionError` from queries | Another writer holds the lease. | Wait; the pool reconnects once the lease is free. |
| `"s3 writer fenced: ..."` | This writer lost its lease to another writer, a commit's answer was lost, an upload failed with `group_commit: true`, or the async uploader gave up. Reads fail too, so nothing stale is served. Durable data (everything with `durability: :sync`, `sync: true`, or before a successful `s3_flush/2`) is not affected; async commits not uploaded yet are lost. | Nothing: the fenced connections disconnect and reconnect by themselves, restoring the latest state from S3. While the other writer holds the lease they fail to connect (see above); once it stops, this repo becomes the writer again. |
| `"Write-write conflict"` | A concurrent transaction changed the same rows. | Retry the transaction. |

**Bounding how long a commit can wait** (with `durability: :sync`; with
`sync: true`, see `:sync_timeout` above). A commit waiting for S3 gives up
when the query's `:timeout` expires (DBConnection then cancels it): the
write fails with `"cancelled while waiting for S3"` within a few milliseconds
of the timeout. Like any lost answer, the upload may still land (see below).
Independently, each S3 request is bounded by the `:s3` options
`:request_timeout_ms` (30 s by default) and `:max_retries` (3).

A commit whose upload reached S3 but whose answer was lost is reported as
failed but can still be durable (the next start restores it). If you need
exactly-once effects, make writes idempotent or check after an error.

## Observability

Besides Ecto's own query events (`[:my_app, :repo, :query]`), sediment
emits telemetry events (see `Sediment.Telemetry`):

* `[:sediment, :query, :start | :stop | :exception]` for every statement,
  with the SQL and the duration;
* `[:sediment, :connection, :disconnect]` with a `:reason`; `:fenced`
  means this writer lost its lease (or an upload failed) and is recovering;
* `[:sediment, :s3, :refresh | :snapshot | :restore, ...]` spans.

For example, to alert when a writer gets fenced, and to chart S3 operations
in Phoenix LiveDashboard:

```elixir
:telemetry.attach("s3-fenced", [:sediment, :connection, :disconnect],
  fn _event, _measurements, %{reason: :fenced, database: db}, _ ->
    Logger.error("S3 writer for #{db} was fenced; reconnecting")
  end, nil)

# in MyAppWeb.Telemetry.metrics/0
summary("sediment.s3.snapshot.stop.duration", unit: {:native, :millisecond}),
summary("sediment.s3.refresh.stop.duration", unit: {:native, :millisecond}),
counter("sediment.connection.disconnect.system_time", tags: [:reason])
```

`Ecto.Adapters.Sediment.s3_info(MyApp.Repo)` returns, e.g. for a health
endpoint: the lease owner and expiry; the current epoch and snapshot; the
uploaded frames and bytes; `durability`, how far the uploader is behind
(`pending_bytes`, `lag_ms`, `durable_offset`, `committed_offset`); and `lost`,
the range of a reported loss (see "Durability").

To see what a workload costs in S3 requests, `Sediment.S3.request_counts/0`
returns the requests this VM has sent so far by operation (`PutObject`,
`GetObject`, ...) and the price class providers bill them in (`"A"`, `"B"`,
`"free"`); compare it before and after, e.g. an hour of production traffic.
sediment's S3 guide describes it and its request log.

## Troubleshooting

| Message | Likely cause |
| ------- | ------------ |
| `s3 store: The operation lacked the necessary privileges ... 403 Forbidden` | Wrong credentials, a bucket policy that denies the writes, or (on SeaweedFS) a bucket that doesn't exist. Create the bucket and check the keys. |
| `this S3 provider does not enforce If-None-Match: * ...` | The provider ignores conditional PUTs, which the single-writer lease depends on; see the provider list above. |
| `s3 lease held by <owner> until <unix ms>` | Another writer is running (or crashed less than `lease_ttl_ms` ago with another owner). The pool retries by itself. |
| `s3 writer fenced: ...` | This node lost the lease or a commit's answer was lost; its connections reconnect by themselves. |
| `s3 config: no database at this S3 prefix` | A replica or `mix ecto.sediment.s3.restore` pointed at an empty prefix (check `:prefix` and `:bucket`). |
| `s3 config: <path> holds a database ..., but the S3 prefix ... has no database; refusing to replace the local file ...` | The repo's `:database` file has tables, and the prefix is empty: a new prefix (existing data isn't uploaded by starting the repo), a mistyped `:prefix`/`:bucket`, or a cleared prefix. Check the bucket and prefix. To upload the data, `mix ecto.sediment.s3.import`; to start empty, move the file (and its `-wal`/`.db-log`) away. |
| `the S3 prefix ... already holds a database; import only into an empty prefix` | `mix ecto.sediment.s3.import` into a prefix that has a database. Check `:prefix`; nothing was changed. |
| `can't import this database: ...` | The file has WITHOUT ROWID or virtual tables (fts5), a hot rollback journal, or can't be read (an encrypted file needs the repo's `:encryption`). The message says which. |
| `restore target exists: <path>` | `mix ecto.sediment.s3.restore`/`s3_restore/3` never replaces a file; pick a new `--output` or remove the old copy (and its `-wal`/`.db-log` files). |
| `s3 config: S3 databases are encrypted by default: ...` | The repo has `:s3` but no `:encryption`: add a key, or `encryption: false` to store the database unencrypted (see "Configuration"). |
| `s3 config: the database at this S3 prefix is unencrypted: ...` | The database in S3 is unencrypted and the repo has no `:encryption`: set `encryption: false`. |
| `s3 config: the database at this S3 prefix is encrypted: ...` | The database in S3 is encrypted and the repo has no `:encryption` option. |
| `s3 config: the restored database can't be read with the given encryption options` | `:encryption` has the wrong key. |
| `s3 commits were lost: ...` from `s3_flush/2` or a `sync: true` write | Acknowledged async commits never reached S3 (the writer was fenced, or stopped while S3 was unreachable); the repo continues from what was durable. Deal with the lost range (see `s3_info/1` `lost`), then call `Ecto.Adapters.Sediment.s3_acknowledge_loss/1`. |
| `s3 corrupt: ...` | Objects under the prefix were deleted or damaged; restore them (e.g. from bucket versioning). |
| `cancelled while waiting for S3` | The query `:timeout` expired while the commit waited for S3; the commit may still land. |
| `Database busy` | With `durability: :sync`, a writer waited longer than `busy_timeout` (15 s for S3 repos) for other writers' uploads; raise it, or batch writes. |
| `DBConnection.ConnectionError ... connection not available` | The pool can't connect, usually for one of the reasons above; the logs show the underlying error. |

Error messages and logs never include the credentials.

## Checkpoints, snapshots and restore times

Each commit appends to a log in S3. A checkpoint uploads a snapshot of the
database and starts a new log, which keeps restores fast; it happens
automatically every `:checkpoint_threshold` bytes of log (an `:s3` option).
Call `Ecto.Adapters.Sediment.checkpoint(MyApp.Repo)` to take one now, for
example before a planned move to another machine; on a running release, via
`bin/my_app rpc "Ecto.Adapters.Sediment.checkpoint(MyApp.Repo)"`. The Mix task
`mix ecto.sediment.checkpoint -r MyApp.Repo` starts the repo itself, so it only
works while the application is stopped (it needs the writer lease). Snapshots are incremental: a
checkpoint uploads only the 64 KiB segments that changed since the previous
snapshot, and a full snapshot again after 16 of those (or when the changes
outgrow it), so a checkpoint costs about as much as the data it changed.

Checkpoints and open transactions:

* `checkpoint/2` waits until transactions open on other connections of the
  repo have finished (they keep their snapshot of the data), so it can take as
  long as the longest one (up to 15 s), and then until the snapshot is
  uploaded.
* Automatic checkpoints are postponed while any transaction is open. Writes
  don't wait, but the log keeps growing, and with it the time a restore takes.
  Avoid long-running transactions on an S3 writer (for example a
  `Repo.stream/2` over a large table inside `Repo.transaction/2`); read such
  data from a replica repo instead.

`Ecto.Adapters.Sediment.s3_info/1` shows the current epoch and snapshot (see
"Observability").

## Point-in-time restore

Set `retain_epochs: n` in the `:s3` options to keep the last `n` epochs
(snapshot plus log). Then restore the state as of any moment in them into a
standalone file:

```sh
mix ecto.sediment.s3.restore -r MyApp.Repo -o /tmp/before-incident.db --at 2026-09-30T08:00:00Z
```

or from code with `Ecto.Adapters.Sediment.s3_restore/3`. The restore only reads
S3: it is safe while the application runs and doesn't affect the writer. It
never replaces a file: the output path must not exist (remove an earlier copy
first), so it can't overwrite the repo's working copy by mistake.
Open the result as a normal (non-S3) Turso database to inspect it or copy
data back. The S3 database itself can't be rolled back in place.

## Costs

An S3-backed repo costs storage plus requests. Each commit (one transaction)
is one class A request (PUT) and one class B request (HEAD); an open writer
also renews its lease with 360 class A requests an hour, even when idle; a
replica refresh lists and downloads only the log objects added since its
last refresh (about 3 requests per refresh, plus one GET per new log
object). With
2026 prices, a 2 GB database at 5 commits/s costs about $72 a month on AWS
S3 or Tigris, and an idle tenant database left open about $1.30 a month,
almost nothing once closed. Batch writes in transactions, refresh replicas
less often, and stop idle tenant repos to cut the bill (see
[Multi-tenant apps](multi_tenant.md)). Sediment's S3 guide,
["Costs"](https://github.com/flmngco/sediment/blob/main/guides/s3.md#costs),
has the measured request counts, the formula, the providers' prices and
worked examples.

## Performance

With `durability: :async` (the default) commits don't wait for S3: they
run at the speed of the local database, and the uploader batches what
accumulates while a PUT is in flight into one object. Only `sync: true`
commits and `s3_flush/2` wait. Reads never touch S3. Through Ecto against a
local SeaweedFS (median, integer primary keys): a single insert takes 0.13 ms
with async durability against 3.9 ms with sync, an `insert_all/3` of 100 rows
2.0 ms against 5.8 ms (`bench/RESULTS.md`, "S3 durability"). With
`AUTOINCREMENT` keys async gains little, another reason to use integer keys.

With `durability: :sync` (and for `sync: true` commits) every commit waits
for S3: one PUT (the log frame) plus one HEAD (an ownership check).
Measured through Ecto in that mode against SeaweedFS behind a proxy that adds a fixed
delay to every chunk sent to S3 (a commit is about 2.5 such delays), 8
writers, 40 commits:

| Added delay | Autocommit writes (`Repo.insert/2`) | `Repo.transaction/2` with `default_transaction_mode: :concurrent` | ... and `group_commit: true` |
| --- | --- | --- | --- |
| 20 ms | 18 commits/s | 20 commits/s | 58 commits/s |
| 50 ms | 8.5 commits/s | 9 commits/s | 28 commits/s |

* A single writer is bounded by the S3 round trips: against real S3, expect
  roughly 10 to 50 commits per second.
* Put related writes in one transaction or use `insert_all/3`: a transaction
  costs one upload no matter how many rows it writes, unless its tables use
  `AUTOINCREMENT` keys (see below).
* Group commit only batches transactions that commit at the same time, i.e.
  `BEGIN CONCURRENT` transactions (MVCC with
  `default_transaction_mode: :concurrent`, or `mode: :concurrent`).
  Autocommit statements take the write lock one at a time and gain nothing.
  With group commit the connections run at `synchronous = FULL`, and a failed
  upload fences the writer until its connections reconnect (automatic).
* With `durability: :sync` writers queue behind uploads, so S3 repos default
  to `busy_timeout: 15_000` (instead of 2 s) to avoid `"Database busy"`
  errors under load.
* Use integer primary keys (see "Primary keys in MVCC mode" in the getting
  started guide): S3 repos run in MVCC mode. With the default `:bigserial`
  keys (`AUTOINCREMENT`), every insert in a `:concurrent` transaction commits
  its id allocation separately, so a transaction inserting 3 rows uploads 4
  log frames and waits for each.

See `bench/RESULTS.md` for the local benchmarks.

## Testing

`mix test --only torture` runs a crash-torture test: a separate VM with four
concurrent Ecto writers (every fifth commit with `sync: true`, plus a process
calling `s3_flush/2` periodically) is killed with SIGKILL at random points
(while restoring at startup, mid-transaction, during checkpoints), with S3
latency varying per round, and a fresh node checks after every kill that the
restored state is a prefix of the commit order holding every durable commit:
with `durability: :async` (the test's default) those made with `sync: true` or
before a successful flush, with `TORTURE_DURABILITY=sync` every acknowledged
one (`TORTURE_ROUNDS` sets the rounds). A 40-round async run: 17,202
acknowledged commits (3,389 with `sync: true`), 46 not yet durable lost at the
kills, no violation. A 100-round run in sync mode: 5,615
acknowledged commits, none lost; 59 kills left the one commit in flight
durable without an acknowledgement, never more than one per kill.

`test/ecto/integration/s3_disaster_recovery_test.exs` in ecto_sediment shows the
scenarios above as tests: restore on a fresh node, lease conflicts and
takeover, checkpoint plus log replay, point-in-time restore, and a VM killed
mid-transaction. `examples/s3_demo` is a runnable walkthrough.
